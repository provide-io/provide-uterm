## 4. Cross-cutting / completeness gaps

- **The biggest miss is the NEW manager `register` path.** 5b's route classification (worker token allowed on `status` + `register`) is itself correct, but `register` is a *full status-record write*, not a constrained self-report — it accepts the operator command-queue fields and lacks the `^[\w\-]+$` agent_id pattern that the sibling `status` route (agent_update.py:117) has. This upgrades finding 7 from "impersonation" to "operator-command injection into another agent," directly undermining the privilege boundary 5b was meant to enforce. Fix `register`'s accepted-field set, not just the token scope.
- **5d frame-isolation `except` is too broad and runs over partially-mutated state** (`websockets_impl.py:254-309`). A failure in broadcast/redaction on a legitimate-but-exotic frame, or a genuine downstream bug, leaves `last_snapshot` mutated while broadcast/event-append never ran, is counted as `ws_worker_frame_invalid_total`, and is `continue`d — silent state inconsistency + masked real defect. ## Completeness assessment: gaps worth a follow-up look

### New gap the dimensions did NOT cover (highest value)

1. **manager-tokens / privilege escalation via `register`'s free-form body — extends finding 7 from "impersonation" to "command injection."** `packages/provide-uterm-platform/src/provide/uterm/manager/routes/agent_ops.py:206-231`. `register_agent(agent_id: str, data: dict[str, Any], ...)` does `model_validate({**base_payload, **data, ...})` over `AgentStatusBase`, which includes the operator-trusted command-queue fields `pending_command_seq` / `pending_command_type` / `pending_command_payload` (models.py:73-75). The low-priv `worker_token` is accepted on this route (5b allow-list), and `agent_id` here has **no** `Path(pattern=...)` validation (unlike the `status` route at agent_update.py:117, which pins `^[\w\-]+$`). So a worker holding the shared worker token can `POST /agent/{victim}/register` with `data={"pending_command_type":"set_goal","pending_command_seq":1,"pending_command_payload":{...}}`, and the next `status` poll for that agent delivers it via `_build_pending_command_response` (agent_update.py:104-107) as a manager command. That is exactly the `set-goal`/`set-directive` operator privilege 5b's scoping was meant to deny the worker token — the down-scoping is undermined because `register` is a full status-record write, not a constrained self-report. 5b's regex/route classification is correct; the gap is that one of the two "self-report" routes is in fact a privileged write primitive. Inspect: constrain `register`'s accepted fields to a self-report subset (exclude `pending_command_*`, `is_hijacked`, `pid`, `paused`), and add the `^[\w\-]+$` agent_id pattern to parity with `status`.

### Cross-cutting / under-examined-class gaps the sweep likely missed

5. **5d frame-isolation `except` is too broad and runs over partially-mutated hub state.** `websockets_impl.py:254-309`. In the `snapshot` branch the order is `make_snapshot_frame` → `update_last_snapshot` (mutates `st.last_snapshot`) → `broadcast` → `append_event`. The per-frame `except (ValidationError, ValueError, KeyError, TypeError)` wraps all four. The fix's premise is "frame builders raise on malformed input" — but the same exception types are raised by `broadcast`/`append_event`/`_redact_frame_fields`/redaction on legitimate frames containing exotic values, and by genuine server-side bugs. When that happens, (a) `st.last_snapshot` is already mutated while the broadcast/event-append never completed (silent state inconsistency), and (b) a real downstream defect is swallowed, counted as `ws_worker_frame_invalid_total`, and `continue`d — masking it as "one bad worker frame." Worth narrowing the try to only the frame-builder calls, or splitting builder-validation from the I/O that follows.

6. **redaction: the `/snapshot` REST egress is the one snapshot path that got NO redaction hook — finding 5 is asymmetric on HEAD, not uniformly open.** Worth calling out precisely: the WS `initial_snapshot` path *did* gain a redaction hook (websockets_impl.py:439-451, gated on `_output_policy_gate` + non-empty rules), but `router_impl.py:628-633 get_last_snapshot` returns `st.last_snapshot` **verbatim** with no gate check at all. So the REST `GET /sessions/{id}/snapshot` (viewer-level `can_read_session`) leaks raw `screen` + `raw_tail` (63854f5) + `prompt_detected` even when an output gate IS configured — and both paths leak in the default no-gate deployment. Re-confirm and fix at `get_last_snapshot` specifically; the WS side is half-covered, the REST side is not covered at all.

7. **resume-quota in-method leak — CONFIRMED valid as shipped.** `register_browser` (connection.py:294-311) increments `_principal_browser_counts` and sets `_ws_principal[ws]`, then awaits `resume_store.create()` — all inside the method, while the route awaits `register_browser` *outside* the `try:` (websockets_impl.py:389, try at 390). A `create()` failure (sqlite IO/locked) or cancellation during that await propagates with the counter incremented and no `finally` to reach `_update_lock_state`'s decrement; no reaper exists for `_principal_browser_counts`. After `max_connections_per_principal` such events the principal is permanently 1008-locked — the exact lockout 30c8002b set out to prevent, one frame deeper than the fix reached. Finding 6 holds.

8. **idp-response-sig: empty-secret HMAC path is reachable at the provider layer.** `auth.py:447` calls `verify_webhook_signature(self.secret or "", ...)`. The *config* validator (config_schema.py:118) refuses `require_signed_response=True` + empty secret, but `WebhookIdentityProvider` constructed directly (tests, embedders, or any non-config code path) with `require_signed_response=True, secret=None` will HMAC with an **empty key** — `verify_webhook_signature("", ...)` computes `hmac.new(b"", ...)`, so any party who knows the body+timestamp (the IdP, or anyone who can replay) can forge a valid signature with a known empty key. The defense rests entirely on the config validator, not on the security-critical function itself. Combined with finding 8 (no entropy/placeholder floor on the secret even via config), the response-signature root-of-trust has no floor at the layer that uses it. Worth a guard inside `verify_webhook_signature` (reject empty `secret`) and/or routing `webhook_idp_secret` through `_is_low_entropy_hmac_secret`.

9. **idp-response-sig replay (finding 9) is unchanged and now interacts with finding 8/this:** signature is over `ts.body` only, no nonce/request-binding, `max_age_s=300`. A single captured signed IdP response is valid for any pending auth for 300s. Confirmed in `webhook_signing.py`; the 1f commit did not bind the response to the outbound request.
